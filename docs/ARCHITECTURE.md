# Устройство установщика

Этот пакет устанавливает новый экземпляр GitPosted. Он не является восстановлением
существующего проекта: production config, публикации, медиа, sessions и старую БД
импортируют отдельной согласованной процедурой. Не направляйте чистый установщик
на действующую БД или чужой web-сайт.

## Границы процессов

```text
SSH: bootstrap.sh (root)
  ├─ проверка ОС, диска, портов и существующих служб
  ├─ проверенный пакет, TLS и отдельный PHP-FPM pool
  └─ фиксированный Unix socket broker (root)
         ↑ JSON, фиксированные действия, проверка UID
HTTPS /install/ → PHP от gitposted-setup
         └─ lib/Wizard.php: enrollment, session, CSRF, input validation
                     ↓ только root broker
         config + schema + регистрация выбранных платформ
                     ↓
         приложение от gitposted, закрытый /install/
```

PHP мастера не получает sudo и не выполняет произвольные команды. Broker принимает
только известные действия и повторно проверяет параметры. Клиент не выбирает
команды, пути, пользователя ОС, SQL или окружение процесса. Unix socket доступен
выделенной группе мастера; сервер проверяет фактический UID клиента через
`SO_PEERCRED`.

Runtime приложения и мастер используют разные UID. Адреса, сертификаты,
службы, конфигурацию nginx и рабочую конфигурацию создаёт root-часть. Любая
операция, способная затронуть существующие сайты/БД, должна завершаться отказом,
а не автоматически удалять или переиспользовать чужие ресурсы.

## Состояние

В `/var/lib/gitposted-installer` находятся:

- `public.json`: безопасные сведения о доступном HTTPS origin, конечном сайте,
  версии и завершении установки. Root владеет файлом, группа мастера читает его.
- `access.json`: ограниченный по времени verifier кода, без исходного кода.
- Закрытое root-состояние broker: verifier enrollment, параметры незавершённой
  установки и её журнал. Пароли и токены не входят в публичный status.
- `sessions/`: `0700`, владелец `gitposted-setup`; PHP sessions и ограничители
  частоты запросов. В session только факт входа, CSRF и времена активности.
- `broker.sock`: root-сервер с доступом только выделенной группы.
- `certbot/`: root-owned venv с режимом `0700`; зависимости не записываются
  внутрь проверяемого неизменяемого пакета установщика.
- `installed.json`: окончательная отметка после успешного переключения nginx.
  После прерывания процесса она восстанавливает terminal status и завершённое
  задание, удаляет pending credentials и закрывает повторный enrollment.

Пароли, токены и API hash передаются в JSON теле через HTTPS, затем через
Unix socket. Они не попадают в URL, аргументы процессов, журнал HTTP, сообщения
об ошибках, PHP session, localStorage или ответы API. Pending-файлы с секретами
доступны только root; рабочий config — только процессу приложения и root.

## Enrollment и HTTP

SSH показывает персональную одноразовую ссылку `https://HOST/install/#setup=TOKEN`.
Ручной ввод кода не нужен. Fragment не передаётся HTTP-серверу; браузер сразу
удаляет его из адресной строки и отправляет token в JSON `login` через HTTPS.
PHP проверяет его формат/verifier, root broker атомарно погашает token через `enroll`; затем PHP
меняет session ID. Повторное использование кода отклоняется. После потери session
или выхода нужна новая ссылка через предусмотренный SSH `--resume`; завершённую
установку это не открывает.

Никакие секреты не принимаются через HTTP. `secure` определяется настоящим SAPI
HTTPS, не пользовательскими `Forwarded`/`X-Forwarded-Proto`. Host разрешён только
списком root. Каждая POST операция требует точного Origin текущего запроса;
после enrollment также требуется CSRF. Cookie имеет Secure, HttpOnly,
SameSite=Strict и путь `/install/`.

Первый HTTPS origin по IP остаётся доступен до завершения. Добавление домена
создаёт отдельный проверенный HTTPS адрес сайта; cookie между IP и доменом не
переносятся. Мастер продолжает работу на исходном IP. Статус разделяет `base_url`
мастера и `site_url`/`admin_url` приложения.

## API и задания

`web/api.php?action=...` возвращает `{ok,result}` либо безопасный
`{ok:false,error:{code,message}}`. `GET status` без входа не показывает CSRF и
подробности задания. Все POST, кроме `login`, требуют `X-CSRF-Token`.

| HTTP действие | Назначение |
|---|---|
| `login` | Автоматическая проверка token персональной ссылки, новая session |
| `logout` | Очистка session |
| `check_bot` | Чтение личности бота и существующих webhook URL; без сообщений |
| `host` | Асинхронная подготовка домена/сертификата |
| `start` | Асинхронная установка из проверенных настроек |
| `retry` | Продолжение конкретного неудавшегося задания |
| `revise` | Исправление настроек неудавшейся установки до начала активации |

Broker дополнительно имеет внутреннее действие `enroll`. В запросе socket —
одна строка JSON `{action,payload}`. Предел запроса 32 КиБ, ответа 64 КиБ;
ожидание broker обычно 5 секунд, проверка бота — до 45 секунд. Длительная
установка и подготовка домена выполняются заданиями, браузер читает status.

Задание имеет `id`, `type` (`host` или `install`), `status`
(`idle/running/failed/complete`) и шаги `pending/running/done/skipped/failed`.
Завершение `host` не означает завершение установки. Install lock и журнал
исключают параллельную установку и повторные внешние действия после replay.

Root checkpoint сохраняет проверенный ID каждого выбранного бота и отдельно
фиксирует начало регистрации до обращения к API. После этого `revise` допускает
новый токен только того же бота с прежним webhook secret; пропуск платформы или
другой ID отклоняются до записи рабочего config. Смена бота доступна в админке
после завершения. В старом незавершённом checkpoint без ID Telegram использует
ID исходного токена; для МАКС сначала требуется подтвердить прежний токен.
После успеха эти bindings удаляются вместе с дубликатами credentials.

Helper запускается отдельной группой процессов от пользователя приложения.
При timeout broker завершает всю группу, включая PHP, и не принимает поздний
результат. Проверка токена ограничена 35 секундами: два read-запроса Telegram
получают по 15 секунд, два read-запроса МАКС — по одной 15-секундной попытке.
Фоновые регистрация и проверка имеют общий предел 300 секунд и штатные
настройки времени/повторов SDK.

Админка ограничивает число WebAuthn-ключей блокировкой MySQL на регистрацию.
Проверка подписи и обновление счётчика выполняются в транзакции с блокировкой
строки ключа; удаление ключа согласовано с этой транзакцией. Уже открытые
административные сессии удаление ключа само по себе не завершает.

## Готовность приложения

В runtime 0.1.1 подтверждённая передача собственного Telegram-канала сохраняет
привязку нового прикладного владельца в существующей `posted_app_settings`.
Она сверяется с точными ID канала и владельца; права бота проверяются отдельно.
Это позволяет получателю управлять каналом в GitPosted без выдачи ему роли
Telegram-администратора. Удаление бота, отзыв привязки и новая человеческая
регистрация учитываются отдельно. Перенос отключённой истории без прежней
валидной привязки не создаёт такую авторизацию.

Telegram-перенос включает source permissions и рекламные категории. При
несовместимых условиях общих grants прежние остатки сохраняются в отдельных
категориях, а существующие legacy-публикации обеих сторон связываются с точным
прежним лимитом. Смена автора, привязки категорий, права и receipt завершаются
в одной транзакции. Прежние ID постов, списанные квоты и повторные подтверждения
сохраняют своё значение. МАКС использует прежний отдельный сценарий переноса.
Для этих изменений не требуется новая таблица или версия схемы.

Обе платформы можно оставить выключенными для установки одной админ-панели.
Для включённых платформ проверяются токен, личность бота и точный webhook.
Существующий сторонний webhook нельзя незаметно заменить: оператор подтверждает
переключение явно. Проверка установки не отправляет посты в каналы.

Config создаётся атомарно; схема применяется явно. Пока необходимые шаги не
завершены, боты выключены. Отказ необязательной платформы не должен приводить
к запуску с наполовину записанным config или к повторной отправке публикаций.
После успеха root помечает установку завершённой и закрывает мутации мастера.

Выходящий доступ к Telegram/MAX и доступность входящего HTTPS проверяются
отдельно. Дополнительная bot MTProto session для импорта ссылок настраивается
отдельно; API ID/hash сами по себе не создают авторизованную session.
