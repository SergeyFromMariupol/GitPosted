# Проверка установщика

Ниже отделены проверки исходников от приёмки на настоящем сервере. Успешный
unit test не означает, что пакеты ОС, выпуск TLS или webhook уже проверены.
Приёмка на выделенной свежей Ubuntu 24.04.4 выполнена для первого пакета;
исправления включены в следующий пакет. Реальные токены ботов не использовались:
подключение платформ проверено отдельными fixtures, а на VPS установлена панель
без подключённых ботов.

Проверены загрузка с публичного GitHub с SHA-256, HTTPS по IPv4 и домену,
автоматический вход по ссылке, сохранение session после подключения домена,
Origin/CSRF, создание 33 таблиц и MAX schema 5, вход в админку без hCaptcha,
страницы обеих платформ, закрытые служебные URL и блокировка мастера.

Реальная установка выявила закрытые права родительских каталогов релиза при
`umask 077`; provisioner теперь создаёт их явно с режимом 0755. Дополнительно
проверены и исправлены путь очистки rate-limit, отдельные лимиты FPM для мастера
и длительных операций приложения, переход в мастер до появления config/schema.

## Локальные проверки без серверных изменений

Из корня пакета:

```bash
php -l lib/Wizard.php
php -l web/api.php
php tests/wizard-test.php
python3 -B tests/provision-test.py
python3 -B tests/broker-review-test.py
php tests/platform-audit-test.php
php tests/wizard-audit-test.php
python3 -B tests/wizard-audit-test.py
python3 -B tests/provision-audit-test.py
node --test tests/wizard-audit-ui.test.cjs
```

Тест мастера использует адаптеры состояния, broker, часов и session в памяти.
Он не открывает MySQL, не читает production config/session, не вызывает Bot API
и не запускает root-команды. К нему добавляются тесты broker/provision и
проверки синтаксиса bootstrap/UI из соответствующих компонентов пакета.

Проверить как минимум:

- Token персональной ссылки принимается только через настоящий HTTPS, атомарно используется один раз,
  меняется session ID. Старый код, cookie, CSRF и просроченная session отклоняются.
- Host, Origin, порт, Fetch Metadata и поддельные forwarded headers не обходят
  проверку. HTTP никогда не принимает credentials.
- Ограничение запросов использует фактический REMOTE_ADDR. Ошибка counter storage
  не отключает ограничение. JSON/type/size/unknown fields проверяются до broker.
- Токены/пароли не попадают в HTTP ответы, PHP sessions, query strings или ошибки.
- Одна платформа, обе платформы и только админ-панель проходят validation;
  выключенные платформы не требуют токена и не активируются случайно.
- Повторный start/retry и параллельные запросы не создают второй install job,
  не перезаписывают рабочую БД и не дублируют регистрацию webhook.
- После installed marker все мутации закрыты. `--resume` не переоткрывает
  завершённый мастер. Подготовка домена сохраняет исходный IP origin/session.
- Сбой после записи `installed.json` восстанавливает terminal status и удаляет
  дубликаты credentials без повторной установки; некорректный marker блокирует
  продолжение. Certbot и Python caches не изменяют проверяемый пакет.
- Root broker проверяет UID сокета, фиксированные actions и повторно валидирует
  payload; произвольные shell/SQL/path/env параметры не исполняются.

## Изолированный прогон PHP, сокета и MySQL

Только на выделенной тестовой Ubuntu с уже установленными зависимостями и
пользователями `gitposted`/`gitposted-setup`:

```bash
sudo python3 -B tests/integration-test.py --run
```

Прогон проходит весь HTTP-мастер, настоящий Unix broker с проверкой UID,
создание MySQL schema и конфигурации, проверку пароля и активацию для четырёх
вариантов: без ботов, Telegram, МАКС, оба. Пятый вариант отзывает проверенный
токен до сохранения config и исправляет его через тот же незавершённый мастер.
Для каждого варианта используются свежие случайные SQL-имена, проверенные на
отсутствие; после прогона удаляются только его БД, пользователь, процессы и
временный каталог. Текущая рабочая БД и config не используются.

API платформ перехватывается внутри временной копии helper. Отправки сообщений
запрещены самим fixture. HTTPS SAPI моделируется loopback-роутером; этот тест
не подтверждает настоящий TLS, nginx, ACME или работу реальных токенов.
Их проверяют отдельно на сервере. Без `--run` скрипт только показывает справку.

Дополнительные regression проверяют ранний сбой apt и продолжение, IPv4 без
IPv6, права и symlink ресурсов, долговечный checkpoint, конкурентный статус,
исправление ошибочного токена до активации, подтверждение переноса чужого
webhook и совпадение MAX webhook secret при замене токена.

## Свежая Ubuntu 24.04 — реальная приёмка

Выполняется только на специально выделенной чистой VPS после подтверждения
оператором её фактического IP и SSH host key. Не использовать production или
сервер с чужими сайтами/базами. Приватные ключи остаются на исходном компьютере.

1. Read-only аудит: ОС/архитектура, память/диск, время, маршруты, занятые
   22/80/443, чужие vhost/БД/cron/службы, доступный исходящий HTTPS.
2. Проверить SHA/происхождение устанавливаемого пакета и отсутствие production
   данных. Записать реальную выполненную команду и версию, скрыв секреты.
3. Выполнить штатный bootstrap. Проверить, что root broker, PHP-FPM мастера и
   приложение работают от предусмотренных разных UID и с закрытыми путями.
4. Открыть показанный IP HTTPS URL. Убедиться, что сертификат действителен и
   относится к серверу. HTTP не позволяет вводить код или токены.
5. Открыть персональную одноразовую ссылку из SSH; вход выполняется автоматически.
   Fragment должен исчезнуть из адресной строки до первого запроса. Проверить
   неверный token, повтор, rate limit и новый session ID. Ручной ввод не нужен.
6. Если нужен домен: подтвердить DNS и выпуск его сертификата. Мастер остаётся
   на исходном IP; конечный `site_url` меняется, cookie не копируется на домен.
7. Установить сначала только админ-панель либо выбранные оператором платформы.
   Проверить вход без заранее настроенной hCaptcha, если она явно выключена;
   password hash, CSRF и throttle остаются активны.
8. Для реальных Telegram/MAX токенов проверить только getMe/bot info и точный
   webhook URL/type/secret. Если токен уже используется, переключение требует
   явного выбора оператора. Не отправлять реальных или тестовых постов.
9. Проверить схему, config mode/owner, CA, HTTPS сайта и `/control/`, единственный
   cron, закрытый web-доступ к CLI/tools и закрытие `/install/` после успеха.
10. Проверить сертификатное продление и таймеры; короткий срок действия IP TLS
    не должен оставлять панель без автоматического продления.
11. Проверить рестарт служб/ОС и корректное восстановление готового приложения.
    Выполнить заранее согласованную имитацию прерванного шага: retry продолжает
    журнал, а не создаёт вторую БД/службу/внешний эффект.
12. Проверить журналы и архив пакета на tokens/passwords/private keys/session.
    Удалить только точные собственные временные файлы, сохранив постоянные данные.

В отчёте перечислить реально пройденные пункты, ошибки, исправления и оставшиеся
pending проверки. Не выдавать работу по fixtures за настоящую установку на VPS
или доставку сообщения ботом. `/start` тоже отправляет сообщение и проверяется
отдельно, когда оператор разрешил такую проверку.
